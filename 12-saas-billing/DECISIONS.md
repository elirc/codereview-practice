# Decisions

Points the spec leaves open, the choice made, and why.

- **Schema objects outside the EF model.** Partial unique indexes, check constraints, the exclusion constraint and the two triggers are created with `migrationBuilder.Sql` and are not declared in the model, so the model snapshot lists only keys, foreign keys and plain indexes. Chosen because the spec asks for these objects as raw SQL; keeping them out of the model avoids two sources for one object.
- **Pending-model-changes check.** EF Core reports a mismatch between the model and the hand-written snapshot as a warning that is logged instead of thrown. The snapshot is maintained by hand, and a cosmetic difference should not stop `migrate` from applying the hand-written SQL.
- **Extra columns.** `plan_items.position` orders plan items (and therefore invoice lines) deterministically; `credit_notes.refund_attempts` counts refund tries for the five-try limit; `credit_balance_transactions.description` stores the reason of a manual adjustment; `created_at` is kept on products, plans, meters and tax rates. None changes a business rule.
- **Catalog reads.** The permission table does not list reading products, plans, meters and tax rates. Every role may read them, because subscribing by plan code needs them and they hold nothing sensitive; only `admin` may change them.
- **Duplicate natural keys.** A second customer with the same `externalId`, plan with the same `code` or meter with the same `code` is `409 already_exists`; the spec names no code for these.
- **Clearing a customer's region.** `PATCH /customers/{id}` treats a missing or null field as "leave unchanged", so an empty string clears `region`.
- **Customer payment token in responses.** The token is not returned; customer representations carry `hasPaymentMethod` instead.
- **Idempotency-Key format.** A missing header is `400 idempotency_key_required`; a header outside 8–128 characters is `400 validation_failed` on the `Idempotency-Key` path. Keys are scoped to the API key that sent them. `404` responses are not stored, since the spec lists only `2xx`, `409` and `422`.
- **Unknown plan code or customer on subscribe.** `404 not_found`; `422 plan_incompatible` is kept for plans that exist but are retired or in another currency.
- **Trial end event.** The trial-to-active transition emits `subscription.trial_ended` only, not also `subscription.updated`, since the spec's event table gives that transition its own type.
- **Billing run claim.** Due subscription ids are read in a batch of 50; each is then locked with `FOR UPDATE SKIP LOCKED` (re-checking status and `next_billing_at`) inside its own transaction, which is held until that boundary's invoice is finalised.
- **Usage for a meter the period's plan does not price.** An event is accepted when any plan of the product sells its meter. If the plan that rates the period does not price that meter, the event is still sealed into the period (so it is billed once) and produces no line.
- **Rating covers only the events of one sealing.** Each sealing rates exactly the rows it marked, so usage sealed earlier into the same period (for example by an upgrade that drops a meter) is never priced a second time.
- **Usage timestamps.** `occurredAt` is truncated to microseconds before it is stored and compared, matching the precision of `timestamptz`.
- **Usage summary periods.** `GET /subscriptions/{id}/usage` reports, per meter, the events billed in the requested period and the unbilled events whose `occurredAt` falls inside it; a trialing subscription has no period and returns `404`.
- **Equal-value plan changes.** A change whose recurring amount is unchanged takes effect at once without an invoice, but the current period keeps the plan it started with for rating usage, the same way a downgrade does. Only an increase moves the current period to the new plan.
- **Meters dropped by an upgrade** are the usage meters of the plan rating the current period that the new plan does not price.
- **Repeated period-end cancellation.** Asking again for `period_end` cancellation of a subscription that is already scheduled returns it unchanged without a new event. `resume` on a subscription that is not scheduled to cancel is `409 invalid_state`. Cancelling a trialing subscription ends it at once whichever mode is given.
- **Immediate cancellation seals usage with `occurredAt < now`,** as the spec says; an event accepted earlier with an `occurredAt` up to five minutes in the future is not billed.
- **Lock order for collection.** Payment transactions A and B, credit notes and voids lock the invoice's subscription (when it has one) before the invoice, matching the subscription → invoice → customer → counter order used by finalisation, because a decline or payment may change the subscription's status.
- **Gateway fake scripting.** Besides the spec's `tok_ok`, `tok_decline_<code>` and `tok_timeout_then_ok`, the fake gateway knows `tok_timeout_unprocessed` (times out, never processed), `tok_ok_then_crash` (processed, then the connection fails) and `tok_ok_refund_fails` (charges succeed, refunds fail). Unknown tokens are declined as `invalid_token`.
- **Credit-note errors not named by the spec.** A line that does not belong to the invoice is `400 validation_failed` on its `invoiceLineId` path. A disposition that does not fit the invoice's state (anything but `reduce_due` on an open invoice, `reduce_due` on a paid one) is `409 invalid_state`.
- **Credit-note tax never exceeds the line's remaining tax.** A partial credit takes the rounded rate share, capped at the tax still uncredited on the line; the final part takes whatever remains.
- **Credit-note year.** The `CN-<year>` counter uses the year of the customer's current civil date, like invoice numbers use the issue date.
- **Failed refunds.** After the fifth failed try the refund is `failed` and `invoice.refundedMinor` drops by its total, as the spec says; the credit note itself and the credited amounts on the invoice lines stay as issued, since credit notes are immutable.
- **Refund calls inside the note's transaction.** The refund loop calls the gateway while it holds the credit note row lock; the credit note id is the refund's idempotency key, so a retried call cannot refund twice.
- **Webhook permissions.** `billing_ops` may list endpoints (secrets are never listed) and list and retry deliveries; creating, changing and rotating endpoints is `admin` only.
- **Endpoints created later.** Fan-out skips endpoints whose `createdAt` is after the event's `createdAt`, so an endpoint added later never receives earlier events even when fan-out runs after it was added.
- **Fan-out with several workers.** Fan-out locks the lowest unfanned event with a blocking `FOR UPDATE`, so events are fanned out one at a time in `sequence` order whatever the number of workers.
- **Deliveries to a disabled endpoint.** A claimed delivery is not sent when it is no longer pending or its endpoint has been disabled in the meantime; it keeps the status it has.
- **Signature key.** `v1` is the HMAC-SHA256 keyed with the UTF-8 bytes of the whole secret string, `whsec_` prefix included.
